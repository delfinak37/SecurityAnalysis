# 1. Роль мониторинга в обеспечении безопасности ИСМУСЭ

**Мониторинг информационной безопасности** — непрерывный процесс сбора, анализа и оценки событий, связанных с состоянием защищённости информационной системы.

Основные задачи:

| Задача | Практическое назначение |
|:--|:--|
| Обнаружение атак | Выявление признаков компьютерных атак |
| Контроль доступа | Выявление подозрительных действий пользователей |
| Контроль конфигураций | Обнаружение несанкционированных изменений |
| Контроль СЗИ | Выявление отключения или неисправности средств защиты |
| Расследование | Получение информации об обстоятельствах инцидента |

**Особенность ИСМУСЭ:** мониторинг должен учитывать не только угрозы конфиденциальности и целостности информации, но и угрозы доступности системы и услуг связи.

---

# Что именно контролируется?

В процессе мониторинга необходимо оценивать три основных направления безопасности:

| Направление | Что контролируется | Пример нарушения |
|:--|:--|:--|
| Конфиденциальность | Доступ к информации | Несанкционированное получение данных |
| Целостность | Неизменность данных и настроек | Подмена конфигурации оборудования |
| Доступность | Работоспособность компонентов | Отказ сервера управления или сетевого узла |

<blockquote>
Для ИСМУСЭ нарушение доступности может иметь непосредственные последствия для управления сетевой инфраструктурой и предоставления услуг связи.
</blockquote>

---

# 2. Центр мониторинга информационной безопасности (SOC)

**SOC (Security Operations Center)** — организационно-технический центр, обеспечивающий мониторинг событий информационной безопасности, выявление угроз и координацию реагирования на инциденты.

Основные функции SOC:

- сбор и анализ событий от компонентов инфраструктуры;
- выявление подозрительной активности и координация действий;
- классификация и приоритизация инцидентов;
- подготовка отчётности о состоянии информационной безопасности.

**Организация SOC:**

| Участник | Основная функция |
|:--|:--|
| Аналитик мониторинга | Первичный анализ событий и оповещений |
| Специалист ИБ | Расследование и оценка инцидентов |
| Системный администратор | Техническое устранение нарушений |
| Ответственный за эксплуатацию сети | Оценка влияния действий на услуги связи |
| Руководитель ИБ | Координация реагирования и принятие решений |

Функции SOC могут выполняться собственной службой организации или специализированным подразделением.

---

# 3. Источники событий информационной безопасности

Для полноценного мониторинга необходимо получать события от всех значимых компонентов ИСМУСЭ.

| Источник | Какие события регистрируются |
|:--|:--|
| Серверы и ОС | Входы, ошибки авторизации, запуск процессов |
| СУБД | Подключения, изменение данных, выполнение запросов |
| Сетевое оборудование | Изменение конфигураций, маршрутизации, состояния интерфейсов |
| Межсетевые экраны | Разрешённые и заблокированные соединения |
| СОВ (IDS/IPS) | Подозрительный трафик, признаки атак |
| Платформа управления | Действия операторов, изменение параметров сети |
| Средства защиты | Срабатывания правил, ошибки и отключение защитных механизмов |

**Принцип:** регистрация должна охватывать как действия обычных пользователей, так и привилегированные операции администраторов.

---

# 4. Архитектура централизованного мониторинга

Для анализа событий различных компонентов используется централизованная система сбора и обработки журналов.

<!-- _class: diagram -->

```text
    ИСТОЧНИКИ СОБЫТИЙ
              │
              ▼
      СБОР ЖУРНАЛОВ И СИГНАЛОВ
              │
              ▼
       ┌───────────────┐
       │     SIEM      │
       │ Сбор и анализ │
       │  корреляция   │
       └───────┬───────┘
               │
        ┌──────┴──────┐
        ▼             ▼
    Оповещение    Инцидент
        │             │
        └──────┬──────┘
               ▼
         РЕАГИРОВАНИЕ
```

**Результат:** события из различных источников объединяются в единую систему, что позволяет анализировать взаимосвязанные действия и выявлять сложные сценарии атак.

---

# 5. SIEM — централизованный анализ событий

**SIEM (Security Information and Event Management)** — система управления событиями и информацией безопасности, предназначенная для сбора, хранения и анализа журналов различных компонентов инфраструктуры.

Основные функции SIEM:

| Функция | Назначение |
|:--|:--|
| Сбор | Получение журналов от источников |
| Нормализация | Приведение событий к единому формату |
| Корреляция | Выявление взаимосвязанных событий |
| Анализ | Поиск признаков подозрительной активности |
| Оповещение | Уведомление специалистов о выявленных угрозах |
| Хранение | Сохранение информации для расследования |

**Принцип работы корреляции:**

SIEM анализирует не только отдельные события, но и их последовательность, время возникновения, источник и взаимосвязь.

---

# Пример: выявление компрометации администратора

Рассмотрим три события, зарегистрированные в ИСМУСЭ.

| Время | Событие | Источник |
|:--|:--|:--|
| 10:15 | Успешная авторизация администратора | Сервер |
| 10:18 | Изменение конфигурации маршрутизатора | Сетевое оборудование |
| 10:20 | Подключение с неизвестного IP-адреса | Межсетевой экран |

**Анализ SIEM:**

- первое событие само по себе может быть штатным;
- второе требует проверки основания для изменения конфигурации;
- третье может указывать на использование скомпрометированной учётной записи.

<blockquote>
Совокупность событий позволяет сформировать оповещение о возможной компрометации администратора, которое требует дополнительной проверки специалистом ИБ.
</blockquote>

---

# 6. Признаки компрометации и подозрительной активности

При мониторинге ИСМУСЭ особое внимание уделяется действиям, способным повлиять на управление сетевой инфраструктурой.

| Направление | Возможные признаки |
|:--|:--|
| Учётные записи | Многочисленные неудачные входы, необычное время авторизации |
| Привилегии | Необоснованное повышение прав, создание новых администраторов |
| Сетевые подключения | Соединения с неизвестных адресов, необычная сетевая активность |
| Конфигурации | Изменение маршрутизации, отключение интерфейсов |
| Средства защиты | Отключение журналирования, остановка защитных служб |
| Программное обеспечение | Запуск неизвестных процессов, появление вредоносных файлов |

**Важно:** отдельный признак не всегда свидетельствует об атаке. Необходимо учитывать контекст, полномочия пользователя, регламент работ и совокупность зарегистрированных событий.

---

# 7. Оценка эффективности средств защиты информации

Наличие средств защиты само по себе не гарантирует защищённость информационной системы. Необходимо оценивать их фактическую эффективность.

| Направление проверки | Что оценивается |
|:--|:--|
| Полнота регистрации | Все ли необходимые события фиксируются |
| Передача журналов | Поступают ли события в централизованную систему |
| Обнаружение атак | Выявляются ли контрольные сценарии угроз |
| Корреляция | Устанавливаются ли связи между событиями |
| Оповещение | Получают ли специалисты информацию об угрозах |
| Реагирование | Выполняются ли действия в установленном порядке |
| Работоспособность СЗИ | Нет ли отключённых или неисправных механизмов |

**Дополнительные показатели оценки:**

- MTTD — среднее время обнаружения инцидента;
- MTTR — среднее время реагирования и восстановления (в зависимости от принятой методики расчёта);

---

# 8. Понятие компьютерного инцидента

**Компьютерный инцидент** — событие, связанное с нарушением или попыткой нарушения безопасности информации, функционирования информационной системы либо с компьютерной атакой.

Примеры инцидентов для ИСМУСЭ:

| Инцидент | Возможные последствия |
|:--|:--|
| Компрометация учётной записи | Несанкционированный доступ |
| Изменение конфигурации маршрутизатора | Нарушение маршрутизации |
| Вредоносное ПО на сервере | Нарушение работы компонентов |
| Атака на сервер управления | Потеря доступности платформы |
| Отключение СЗИ | Снижение уровня защищённости |
| Несанкционированный доступ к СУБД | Нарушение конфиденциальности или целостности данных |

При обработке инцидента необходимо определить его масштаб, источник, затронутые компоненты и возможные последствия.

---

# Событие или инцидент: в чём разница?

| Понятие | Характеристика | Пример |
|:--|:--|:--|
| Событие ИБ | Зарегистрированное действие или изменение состояния | Вход администратора |
| Подозрительное событие | Действие с признаками возможного нарушения | Вход с неизвестного адреса |
| Компьютерный инцидент | Подтверждённое нарушение или попытка нарушения безопасности | Несанкционированное изменение конфигурации |

<blockquote>
Не каждое событие является инцидентом. Сначала необходимо провести анализ и установить характер произошедшего.
</blockquote>

---

# 9. Основные этапы реагирования на инциденты

Реагирование представляет собой последовательность организационных и технических действий, направленных на устранение угрозы и восстановление безопасного функционирования системы.

| Этап | Содержание работ |
|:--|:--|
| 1. Обнаружение | Получение сигнала от SIEM, СОВ или другого источника |
| 2. Анализ | Проверка события, определение масштаба и характера инцидента |
| 3. Локализация | Ограничение распространения угрозы |
| 4. Устранение | Удаление вредоносных компонентов, устранение причины |
| 5. Восстановление | Возвращение системы к штатной работе |
| 6. Анализ результатов | Документирование и принятие мер профилактики |

**Последовательность реагирования:**

```text
ОБНАРУЖЕНИЕ
     ↓
АНАЛИЗ И ОЦЕНКА
     ↓
ЛОКАЛИЗАЦИЯ УСТРАНЕНИЕ ПРИЧИНЫ
     ↓
ВОССТАНОВЛЕНИЕ и АНАЛИЗ РЕЗУЛЬТАТОВ
```

---

# 10. Особенности реагирования в ИСМУСЭ

ИСМУСЭ обеспечивает мониторинг и управление сетями электросвязи. Поэтому инциденты информационной безопасности могут непосредственно повлиять на предоставление услуг связи.

При реагировании необходимо учитывать:

- непрерывность функционирования сетевой инфраструктуры;
- критичность затронутых узлов и оборудования;
- наличие резервных каналов и компонентов;
- возможность изоляции отдельного сегмента;
- согласование технических действий с ответственными за эксплуатацию сети.

**Пример:** при обнаружении несанкционированного изменения конфигурации маршрутизатора немедленное отключение оборудования может привести к нарушению связи.

Сначала необходимо определить затронутые соединения, оценить последствия и выбрать безопасный способ локализации угрозы.

---

# Выбор способа локализации инцидента

| Ситуация | Возможные действия |
|:--|:--|
| Компрометация учётной записи | Блокировка или ограничение доступа, смена учётных данных |
| Изменение конфигурации | Проверка изменений, восстановление проверенной конфигурации |
| Вредоносное ПО на сервере | Изоляция узла с учётом его роли и резервирования |
| Подозрительный сетевой трафик | Ограничение соответствующих соединений |
| Отключение средства защиты | Восстановление работы СЗИ, проверка причины отключения |

<blockquote>
Выбор действий определяется масштабом угрозы и последствиями для функционирования системы. Изоляция компонентов не должна приводить к необоснованному прекращению предоставления услуг связи.
</blockquote>

---

# 11. Взаимодействие с ГосСОПКА

**ГосСОПКА** — государственная система обнаружения, предупреждения и ликвидации последствий компьютерных атак, обеспечивающая координацию деятельности по противодействию компьютерным атакам на информационные ресурсы.

Основные направления взаимодействия:

- передача информации о компьютерных инцидентах и взаимодействие с уполномоченными подразделениями;
- получение информации об актуальных угрозах и компьютерных атаках;
- участие в мероприятиях по предупреждению и ликвидации последствий атак;
- предоставление информации для анализа инцидентов.

**Нормативная основа взаимодействия:**

| Документ | Назначение |
|:--|:--|
| Приказ ФСБ №367 от 24.07.2018 | Перечень информации и порядок её представления в ГосСОПКА |
| Приказ ФСБ №282 от 19.06.2019 | Информирование ФСБ о компьютерных инцидентах и реагирование на них в отношении значимых объектов КИИ |
| Приказ ФСБ №554 от 26.12.2025 | Требования к средствам обнаружения, предупреждения и ликвидации последствий компьютерных атак и реагирования на инциденты |

**Важно:** порядок взаимодействия, состав передаваемой информации и сроки определяются применимыми нормативными требованиями.

---

# 12. Журналирование и сохранение цифровых доказательств

При расследовании компьютерного инцидента необходимо сохранить сведения, позволяющие установить обстоятельства произошедшего.

| Источник | Какие материалы сохраняются |
|:--|:--|
| Операционные системы | Журналы авторизации, запуска процессов |
| СУБД | Журналы подключений и операций с данными |
| Сетевое оборудование | Журналы изменений конфигураций |
| SIEM и СОВ | События, оповещения, результаты корреляции |
| Межсетевые экраны | Сведения о сетевых соединениях |
| Служебная документация | Заявки на работы, согласования, карточки инцидентов |

**Основные требования к сохранению материалов:**

- сохранение исходных данных и фиксация времени событий;
- защита журналов от несанкционированного изменения;
- ограничение доступа к материалам расследования;
- документирование действий специалистов;
- обеспечение возможности проверки достоверности сохранённых данных.

---

# 13. Практический пример: несанкционированное изменение конфигурации

**Исходная ситуация**

В системе мониторинга ИСМУСЭ обнаружено изменение конфигурации сетевого оборудования. Операция выполнена с использованием учётной записи администратора, однако соответствующая работа не была запланирована.

**Ход расследования:**

| Шаг | Действие специалиста |
|:--|:--|
| 1 | SIEM регистрирует событие и формирует оповещение |
| 2 | Проверяются учётная запись, время операции и история изменений |
| 3 | Устанавливается, было ли изменение санкционировано |
| 4 | Определяется влияние конфигурации на сетевые соединения |
| 5 | При подтверждении инцидента ограничивается доступ скомпрометированной учётной записи |
| 6 | При необходимости восстанавливается проверенная конфигурация |
| 7 | Сохраняются журналы и другие материалы расследования |
| 8 | Инцидент документируется, определяется необходимость информирования ГосСОПКА |

**Ожидаемый результат:** угроза устранена, работоспособность системы сохранена, обстоятельства инцидента задокументированы.

---

# 14. Практическая проверка мониторинга и реагирования

При аудите ИСМУСЭ необходимо проверить не только наличие средств защиты, но и работоспособность всего процесса мониторинга.

| Этап | Проверяемое действие | Ожидаемый результат |
|:--|:--|:--|
| Э1. Источники | Проверка перечня компонентов и источников событий | Определены все значимые источники |
| Э2. Журналирование | Проверка регистрации событий | Необходимые действия фиксируются |
| Э3. Передача | Проверка поступления журналов в SIEM | События централизованно собираются |
| Э4. Обнаружение | Проверка контрольных сценариев | Подозрительные действия выявляются |
| Э5. Реагирование | Учебная отработка инцидента | Действия выполняются по регламенту |
| Э6. Документирование | Проверка карточки инцидента и доказательств | Результаты расследования сохранены |

<blockquote>
Проверочные действия, способные повлиять на производственную инфраструктуру, следует проводить на согласованном стенде либо в безопасных условиях с учётом непрерывности услуг связи.
</blockquote>

# Типичные недостатки, выявляемые при аудите

| Код | Недостаток | Возможное последствие |
|:--|:--|:--|
| Т1 | Не все компоненты передают события | Неполная картина происходящего |
| Т2 | Журналирование настроено некорректно | Потеря важных сведений |
| Т3 | Нет централизованного анализа событий | Сложность выявления комплексных атак |
| Т4 | Не настроены сценарии обнаружения | Пропуск подозрительной активности |
| Т5 | Отсутствует регламент реагирования | Несогласованные действия специалистов |
| Т6 | Журналы не защищены от изменения | Потеря достоверности доказательств |
| Т7 | Не учитывается влияние локализации на услуги связи | Нарушение доступности инфраструктуры |

**Результат аудита:** формирование перечня замечаний и рекомендаций по совершенствованию мониторинга, защиты и реагирования.

# Итоги лекции

- Мониторинг позволяет своевременно выявлять подозрительную активность и компьютерные атаки.
- SOC обеспечивает организацию мониторинга и координацию реагирования.
- SIEM выполняет централизованный сбор и корреляцию событий.
- Эффективность СЗИ определяется не только их наличием, но и реальной способностью обнаруживать угрозы.
- Реагирование включает обнаружение, анализ, локализацию, устранение последствий и восстановление.
- При защите ИСМУСЭ необходимо учитывать непрерывность предоставления услуг связи.
- Сохранение журналов обеспечивает возможность полноценного расследования инцидентов.

**Главная задача:** обеспечить своевременное обнаружение и устранение угроз без необоснованного нарушения функционирования ИСМУСЭ.
